## Сделать
- Миграция — номер выдаёт оркестратор. Таблица записей об отправленном: `tenant`, учётная запись, метка (уникальна),
  хэш Message-ID (индекс), адресаты (массив, индекс GIN), беседа, время; RLS; очистка `purge_before` — по индексу
  времени, порциями.
- Беседы: таблица бесед (`ThreadId`, учётная запись, время создания), привязка письма к беседе (письмо — одна беседа,
  неизменяема), ключи присоединения (`Message-ID` писем беседы — индекс по учётной записи и ключу); память беседы для
  аномалий — типы вложений, домены ссылок, `Reply-To` (ограниченные массивы). RLS.
- Удержание беседы и действия по беседе — таблицы с RLS; удержание — кто, когда, основание.
- `SentLog`, `ThreadStore` и политики беседы в `PgMeta` по контракту CTR-94: методы над транзакцией `ingest`, без
  отдельного соединения; `before_final_delete` письма удержанной беседы — одним запросом.
- Существующие письма: привязка к беседам — фоновой задачей по `thread_key` (`MessageMeta`), без простоя.

## Как делают другие
- Rspamd `replies` хранит хэши Message-ID в Redis 1 день (https://docs.rspamd.com/modules/replies); у нас — PostgreSQL
  со сроком `smtp.reply.max_age` (30 дней), чтобы признак переживал перезапуск и работал на всех узлах.
- Удержание треда целиком — Google Vault (https://support.google.com/vault/answer/2535539).

## Приёмка
- Наборы `tp-testkit` `suite::reply` и `suite::thread` проходят на `PgMeta` (PostgreSQL) наравне с памятью.
- Тест миграции: таблицы поверх предыдущей, повторный запуск ничего не меняет; фоновая привязка старых писем —
  письма одного `thread_key` в одной беседе.
- Сбой в середине `ingest` не оставляет привязки без письма и письма без беседы (откат транзакции).
