# 3. Хранение данных

## 3.1. Контур метаданных (PostgreSQL)

В PostgreSQL хранятся: структура ящиков и папок, свойства писем (идентификаторы, заголовки для списков, дата, флаги, MODSEQ), ACL и делегирование, скрипты Sieve, календари и контакты, очередь SMTP, задания индексации (outbox), учёт BLOB (хэш, поколение, счётчик ссылок), манифесты поисковых индексов, справочник шардов. Тела писем и вложения в PostgreSQL не хранятся.

Требования к СУБД:

- PostgreSQL 16 и выше без дополнительных расширений;
- совместимость по стандарту, а не по продукту: протокол и диалект PostgreSQL; используются только встроенные механизмы (RLS, `SELECT … FOR UPDATE SKIP LOCKED`, рекомендательные блокировки, LISTEN/NOTIFY, jsonb, `INSERT … ON CONFLICT`); совместимые СУБД (в том числе сертифицированные ФСТЭК России) допускаются без доработки продукта;
- Enterprise — кластер с синхронной репликой (не менее двух кандидатов на роль синхронной реплики), RPO = 0, автоматическое переключение с исключением одновременной записи на двух серверах, RTO ≤ 30 с; механизм высокой доступности выбирает заказчик;
- адрес primary для узла — одним из способов: список адресов (узел выбирает доступный для записи, семантика `target_session_attrs=read-write`), единый адрес (VIP, DNS, прокси), Service Kubernetes;
- Enterprise — PgBouncer 1.21+ в режиме transaction (с поддержкой prepared statements); соединение-слушатель сигналов (п. 2.8) — напрямую к primary;
- рабочий набор (горячие ящики, индексы БД) размещается в RAM, хранилище — SSD/NVMe.

Права в СУБД разделены: владелец схемы применяет миграции и в работе узлов не используется; роли узлов получают только необходимые права (например, роли search и indexer не изменяют метаданные писем); журнал аудита и журнал доставки доступны приложению только на добавление и чтение.

Поведение узла при переключении primary:

- признаки — обрыв соединения, коды `25006` (транзакция только для чтения) и `57P01` (остановка сервера); узел сбрасывает пул, находит новый primary и повторяет операции с нарастающей паузой;
- повторяются только идемпотентные операции (по идентификатору письма, ключу журнала событий); исход фиксации при обрыве во время COMMIT устанавливается по этому ключу;
- на время переключения действует ограничение потока (п. 6.3): SMTP — временный отказ 4xx, IMAP и JMAP — временная ошибка; письма в памяти не накапливаются;
- аренды и рекомендательные блокировки захватываются заново, номер эпохи аренды исключает действия прежнего владельца; соединение-слушатель переподключается, подписчики сверяются с хранилищем (п. 2.8);
- длительность переключения и число повторов публикуются в метриках.

Продукт не управляет кластером СУБД; команда thepost doctor проверяет соответствие СУБД требованиям. Эталонные стенды: pg_auto_failover (ВМ), CloudNativePG (Kubernetes); Postgres Pro (встроенная отказоустойчивость BiHA) — в матрице совместимости; Patroni допустим, если у заказчика разрешено исполнение Python (п. 7.1).

**Обоснование выбора PostgreSQL.** Метаданные почты — транзакционная нагрузка с частыми точечными изменениями (флаги, перемещения), требующая строгой согласованности. PostgreSQL — наиболее распространённая открытая транзакционная СУБД с развитыми средствами HA и резервного копирования и доступными компетенциями. Альтернативы рассмотрены и отклонены (приложение Б).

**Обоснование выноса HA за пределы продукта.** Высокая доступность СУБД — самостоятельная зрелая задача, которую заказчики Enterprise-класса решают штатными средствами. Встраивание оркестратора повторяет функции готовых средств (pg_auto_failover, CloudNativePG, Patroni, встроенные механизмы СУБД) и привязывает заказчика к одному варианту; продукт задаёт требования к результату и собственное поведение при переключении.

**Обоснование PgBouncer.** При десятках и сотнях узлов приложения число соединений превышает возможности PostgreSQL (каждое соединение — отдельный процесс). Пул в режиме transaction ограничивает число серверных соединений независимо от числа узлов.

## 3.2. Контур бинарных объектов (BLOB)

Тела писем, MIME-части и сегменты поисковых индексов хранятся в BLOB-хранилище через интерфейс BlobStore с двумя реализациями: локальная POSIX-директория (SMB) и S3 API (Enterprise; эталонная реализация — SeaweedFS). Объекты неизменяемы; ключ объекта — tenant/sha256/gen. Объекты сжимаются (zstd) перед записью, если это уменьшает размер; хэш вычисляется от исходного содержимого, признак сжатия хранится в учёте BLOB; уже сжатые форматы (архивы, изображения, видео) не сжимаются повторно.

Каждый узел приложения использует локальный NVMe как LRU-кэш горячих объектов и сегментов индексов. Кэш не является источником истины и может быть очищен в любой момент.

**Обоснование.** Разделение контуров позволяет масштабировать объём (объектное хранилище на недорогих дисках) независимо от производительности метаданных (NVMe), снимает ограничения файловых систем по числу inode и упрощает расширение до петабайтных объёмов. Неизменяемость и адресация по содержимому делают запись идемпотентной и упрощают репликацию и восстановление. Единый интерфейс для диска и S3 обеспечивает одну логику во всех профилях.

## 3.3. Дедупликация

Входящее письмо разбирается на MIME-части. Части (тела и вложения) сохраняются как отдельные объекты, адресуемые хэшем SHA-256; заголовки, уникальные для получателя (Received, Delivered-To, Return-Path), хранятся отдельно. При доставке письма нескольким получателям и при повторной пересылке вложения объект хранится в одном экземпляре. Дедупликация выполняется только в пределах одного tenant (организации).

**Обоснование.** Письмо целиком у разных получателей различается заголовками трассировки, поэтому его дедупликация неэффективна; основной объём дают вложения. Ограничение tenant исключает канал утечки «подтверждение наличия файла» между организациями и позволяет использовать раздельные ключи шифрования хранилища.

## 3.4. Протокол записи и удаления BLOB

Запрещено обращаться к BLOB-хранилищу внутри открытых транзакций PostgreSQL. Учёт объектов ведётся в таблице blobs: хэш, поколение (gen), счётчик ссылок (refcnt), состояние (live, deleting), момент обнуления счётчика.

Запись:

1. вычисляется хэш части при потоковом разборе письма;
2. если существует запись live с этим хэшем — счётчик ссылок увеличивается на число получателей одной транзакцией, загрузка не выполняется;
3. иначе объект загружается по ключу hash/gen, затем создаётся запись live; если запись в этот момент находится в состоянии deleting, поколение увеличивается и объект загружается по ключу hash/gen+1;
4. метаданные письма фиксируются короткой транзакцией после успешной загрузки.

Удаление:

1. удаление пользователем переносит элемент в корзину (п. 4.7), ссылки сохраняются;
2. окончательное удаление уменьшает счётчики ссылок; при обнулении фиксируется момент обнуления;
3. GC одной транзакцией переводит запись в deleting при условии refcnt = 0 и истечения окна W (п. 3.5), удаляет объект hash/gen из хранилища и удаляет запись, только если поколение не изменилось.

Поиск «сирот»: объекты хранилища старше периода ожидания, для которых нет записи с совпадающими хэшем и поколением, удаляются. Период ожидания превышает максимальную длительность загрузки объекта.

**Обоснование.** Схема исключает гонку «GC удаляет объект, на который в этот момент ссылается новое письмо» без распределённых блокировок, ожиданий и повторов: атомарность обеспечивает одна строка PostgreSQL, повторная загрузка по ключу из хэша идемпотентна. Конкуренция за счётчик при массовой рассылке снимается одной операцией на всех получателей письма.

## 3.5. Консистентность при восстановлении (инвариант W)

Инвариант W: любой объект, на который ссылаются метаданные в любой доступный для восстановления момент времени, существует в BLOB-хранилище. Инвариант обеспечивается двумя правилами:

- объект записывается раньше метаданных, ссылающихся на него;
- физическое удаление объекта выполняется не ранее окна W после обнуления ссылок; W не меньше глубины самой старой точки восстановления (окно PITR, глубина DR-реплики, срок хранения снапшотов).

При выполнении инварианта метаданные и BLOB-хранилище восстанавливаются на любые точки в пределах W независимо, без координации резервных копий. После восстановления команда thepost verify выполняет сверку в обе стороны: удаляет «сирот», помечает письма с отсутствующими объектами как повреждённые и пытается восстановить объекты из реплики.

При межсайтовом DR с асинхронной репликацией RPO по телам писем равен отставанию репликации объектного хранилища. В модуле «Межсайтовый DR» (п. 1.3) доставка подтверждается отправителю только после репликации объекта на резервную площадку (ценой увеличения задержки доставки).

**Обоснование.** Согласованность обеспечивается свойством данных (неизменяемость и отложенное удаление), а не процедурой резервного копирования: не требуются синхронизация снапшотов двух систем и распределённые транзакции, которые S3 не поддерживает. Цена — дополнительный объём под удалённые за окно W данные (обычно единицы процентов).

## 3.6. Шардирование метаданных и перенос ящиков

Схема БД с первого выпуска проектируется с учётом шардирования: ключи всех таблиц ящика содержат tenant_id и account_id, внешние ключи между ящиками отсутствуют. Справочник шардов сопоставляет ящик с кластером PostgreSQL; адрес шарда хранится без пароля, учётные данные — ссылкой на секрет (п. 6.7). В базовой поставке справочник содержит один шард; размещение ящиков на нескольких кластерах (новые ящики — на наименее загруженном шарде) и перенос ящиков реализуются модулем «Шардирование» (п. 1.3).

Перенос ящика между шардами выполняется в фоне через Admin API: копирование метаданных, догоняющая синхронизация по MODSEQ, кратковременная (секунды) блокировка записи, переключение в справочнике. BLOB не переносятся.

Один кластер PostgreSQL обслуживает до 10⁵–10⁶ ящиков (подтверждается на стенде, приложение Д); шардирование включается сверх этого объёма.

**Обоснование.** Шардирование по ящикам — естественная граница данных почты (аналог баз почтовых ящиков Exchange), но за счёт выноса тел писем в BLOB оно требуется на порядок позже. Учёт шардов в схеме с первого выпуска исключает её переработку при росте.

## 3.7. Миграция BLOB-бэкенда без остановки

Функция реализуется модулем «Миграция бэкенда» (п. 1.3). Заделы базовой поставки: ключ объекта не зависит от бэкенда, интерфейс BlobStore допускает составную реализацию.

Конфигурация BlobStore поддерживает составной тип migration с параметрами source и target. В режиме миграции:

- новые объекты записываются только в target;
- чтение выполняется из target, при отсутствии объекта — из source (одна дополнительная операция чтения);
- мигратор (роль maintenance) с низким приоритетом обходит source, копирует объекты в target, проверяет SHA-256 и фиксирует перенос; удаление из source — после фиксации переноса и истечения окна W;
- GC в режиме миграции удаляет объекты из обоих бэкендов;
- пропускная способность мигратора ограничивается параметром, изменяемым без перезапуска.

Сегменты поисковых индексов хранятся в том же BlobStore и переносятся вместе с письмами; переиндексация не требуется. Метрики процесса: mail_migration_total_bytes, mail_migration_processed_bytes, mail_migration_errors_total, mail_migration_eta_seconds.

**Обоснование.** Переход SMB → Enterprise и замена хранилища выполняются без простоя и без отдельного инструмента; хранение индексов в BlobStore сводит миграцию поиска к переносу объектов.

## 3.8. Организации (tenant)

Модель данных и API с первого выпуска учитывают несколько организаций (tenant); в базовой поставке существует одна организация по умолчанию.

- домены (одна организация может иметь несколько доменов), ящики, группы, общие ящики, политики принадлежат организации;
- tenant_id входит в ключи всех таблиц и в ключи объектов BLOB (п. 3.2); все запросы выполняются в контексте организации; дополнительный рубеж — политики RLS PostgreSQL по tenant_id (параметр сеанса устанавливается в начале каждой транзакции, что совместимо с PgBouncer в режиме transaction);
- в пределах организации действуют дедупликация (п. 3.3), GAL, free/busy, делегирование, общие ящики, поиск по множеству ящиков;
- политики (квоты, сроки хранения, лимиты отправки, ключи DKIM, профиль Milter) разрешаются по цепочке «организация → домен → ящик», для политик хранения — до папки;
- каталог и поставщик удостоверений подключаются к организации (в базовой поставке — один каталог);
- ресурсы Admin API адресуются в контексте организации; роли администраторов имеют область действия — вся инсталляция или организация;
- метрики и журнал аудита содержат идентификатор организации.

Создание нескольких организаций и функции изоляции (отдельные каталоги и поставщики удостоверений, делегированное администрирование, ограничения и отчёты потребления организации, раздельные ключи шифрования) реализуются модулем «Мультитенантность» (п. 1.3).

**Обоснование.** Добавление организации в ключи и запросы после первого выпуска потребовало бы переработки схемы и всех запросов. RLS исключает утечку данных между организациями при ошибке в запросе приложения.
