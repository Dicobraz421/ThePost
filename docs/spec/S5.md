# 5. Интеграция и администрирование

## 5.1. Каталог и аутентификация

- службы каталогов — LDAPS (FreeIPA, Samba AD, Microsoft AD): учётные записи, группы, атрибуты GAL; синхронизация инкрементальная;
- Kerberos — SASL GSSAPI для IMAP и SMTP, SPNEGO для HTTP;
- OpenID Connect — SASL OAUTHBEARER (RFC 7628) для IMAP и SMTP, Bearer-токены для JMAP, DAV и Admin API;
- пароли приложений — для клиентов без поддержки Kerberos и OAUTHBEARER; выпуск и отзыв через Admin API;
- SAML 2.0 — вместе с веб-клиентом (приложение Е).

**Обоснование.** IMAP и SMTP не поддерживают SAML и OIDC напрямую; стандартный способ использовать токены OIDC в этих протоколах — SASL OAUTHBEARER. SAML применим только к веб-входу и без веб-интерфейса не используется.

## 5.2. Административный API

Admin REST API (спецификация OpenAPI) — единственный интерфейс управления: организации, ящики, домены, политики, квоты, права, пароли приложений, экспорт и импорт, корзина, журнал аудита; операции модулей (перенос ящиков, Legal Hold, режим миграции бэкенда и др.) — при включённом модуле. Аутентификация — OIDC с ролевой моделью администраторов. Все операции администраторов записываются в журнал аудита и экспортируются по OTLP.

## 5.3. Резервное копирование и восстановление

Продукт предоставляет сервисные функции; резервное копирование выполняют внешние СРК заказчика.

**Таблица: Уровни восстановления**

| Уровень | Объект | Механизм | Роль продукта |
|---|---|---|---|
| Недавно удалённое | Письмо, папка, событие, контакт в пределах срока корзины | Корзина (п. 4.7) | Полностью внутри продукта |
| Точечное из архива | Ящик, папка, календарь, контакты, Sieve, ACL на дату | Внешняя СРК по расписанию забирает инкрементальный экспорт через Admin API и возвращает его при восстановлении | Инкремент по токену изменений (MODSEQ, состояние JMAP); восстановление в исходный или другой ящик; исключение дублей (Message-ID и хэш); восстановление структуры и прав; идемпотентность; открытый формат (EML, iCalendar, vCard, JSON-манифест) |
| Кластер, DR | Все данные | Внешние средства напрямую: PITR PostgreSQL (pgBackRest или аналог), репликация и снапшоты объектного хранилища | Инвариант W (п. 3.5), сверка thepost verify |

Продукт не выполняет резервное копирование учётных записей (источник истины — каталог), конфигурации (хранится в системе управления конфигурацией) и очереди SMTP (восстанавливается вместе с PostgreSQL).

**Обоснование.** Аварийное восстановление больших объёмов эффективно только средствами самих хранилищ — копирование через API на петабайтных объёмах неприменимо. Точечное восстановление требует знания модели данных, поэтому его логика находится в продукте, а планирование и хранение копий — в СРК заказчика.

## 5.4. Миграция с внешних систем

Функции импорта из внешних систем (Microsoft Exchange и др.) не встраиваются в ядро. Ядро предоставляет Admin API импорта (п. 5.2) и JMAP; утилиты миграции (EWS, PST, IMAP) — в дорожной карте (приложение Е).

**Обоснование.** Миграция — разовая ресурсоёмкая операция; её выполнение вне ядра исключает влияние на промышленную нагрузку.

## 5.5. Конфигурация

- минимальная конфигурация содержит три параметра: адрес PostgreSQL, адрес BLOB-хранилища, основной домен; остальные параметры имеют значения по умолчанию или рассчитываются автоматически от ресурсов узла;
- все пороговые значения, таймауты, интервалы, лимиты и размеры кэшей задаются в config.yaml и применяются без перезапуска (hot reload), кроме параметров, явно отмеченных в документации;
- параметр `roles` задаёт роли узла пресетами или списком (п. 2.1); секции `modules.<имя>` — конфигурацию модулей (п. 2.5);
- структура config.yaml описана в JSON Schema, поставляемой с выпуском; конфигурация проверяется по схеме при запуске и при hot reload;
- команда thepost doctor проверяет окружение: версию и настройки СУБД, доступ к BLOB-хранилищу, DNS (MX, SPF, DKIM, DMARC, MTA-STS, PTR), сертификаты, балансировщик (PROXY v2), синхронизацию времени; результат выводится в текстовом и машиночитаемом (`--json`) виде.

**Обоснование.** Сложность эксплуатации не должна превышать Exchange: минимум обязательных параметров, автоматическая настройка, самодиагностика. Настраиваемость всех порогов необходима также для эмуляции масштаба на стенде (приложение Д).

## 5.6. Средства развёртывания

- эталонные Ansible-роли (ВМ) и Helm-чарт (Kubernetes) для всех профилей и пресетов ролей;
- эталонная установка SMB одной командой: бинарный файл, PostgreSQL, Rspamd на одной ВМ (п. 1.2);
- графический редактор топологии и автоматическая установка по ней — модуль «Развёртывание» (п. 1.3), использующий эталонные Ansible-роли и Helm-чарт без собственного агента на узлах.

**Обоснование.** Эталонные средства закрывают типовые установки без отдельного инструмента; графический редактор строится поверх них, поэтому не дублирует логику установки.
