# Приложение З. Схемы развёртывания

Приложение описывает поддерживаемые схемы развёртывания (п. 2.9): для каждой — когда её выбирать, из чего она состоит, ограничения компонентов и поведение при отказах. Во всех схемах используется один и тот же бинарный файл; схемы различаются числом узлов, пресетами ролей (п. 2.1) и внешними компонентами. Размеры ВМ — ориентиры, уточняются на стенде (приложение Д).

Термины: узел — экземпляр `thepost` с набором ролей по пресету; RPO — допустимая потеря данных; RTO — время восстановления работы.

## З.1. SMB

Для организаций до 1 000 ящиков без требования отказоустойчивости средствами продукта. Всё работает на одной ВМ: сам сервер со всеми ролями, PostgreSQL, OpenBao и Rspamd; тела писем и поисковые индексы лежат на локальном диске. Отказ физического сервера закрывает гипервизор: ВМ перезапускается на другом хосте кластера (например, Proxmox HA), если её диск — на общем хранилище. Потерю данных закрывает резервное копирование: архив журнала PostgreSQL (pgBackRest) и копия каталога BLOB.

Схема: deploy-smb.svg — SMB: одна ВМ

**Таблица: Состав схемы SMB**

| Компонент | Кол-во | Назначение | Ограничения |
|---|---|---|---|
| ВМ (4 vCPU, 8 GB RAM, NVMe — объём почты × 1,3) | 1 | Все компоненты | Единственная точка отказа; рост — только добавлением ресурсов ВМ |
| thepost, пресет all | 1 процесс | Все роли, сигналы и кэш — в памяти процесса | До 1 000 ящиков; обновление — перезапуск на секунды |
| PostgreSQL | 1 | Метаданные | Без реплики: восстановление — из архива на момент времени |
| Локальный диск | 1 | Тела писем, вложения, сегменты индексов | Объём ограничен диском ВМ; переход на S3 — плановое окно или модуль «Миграция бэкенда» |
| OpenBao | 1 | Секреты | Ключ распечатывания на сервере (риск 16) |
| Rspamd, clamav-milter | 1 | Антиспам и антивирус по Milter | clamav-milter — по желанию, требует ~1,5 GB RAM |

Поведение при отказах:

- отказ хоста — перезапуск ВМ гипервизором, RTO — минуты;
- отказ диска или ВМ без общего хранилища — восстановление из резервной копии, RPO — частота копирования BLOB, для метаданных — секунды (архив WAL);
- обновление продукта — перезапуск процесса, клиенты переподключаются.

## З.2. Малый Enterprise

Для небольших организаций, которым нужна работа без простоя при отказе одного сервера. Два одинаковых узла с пресетом mailbox (все роли, кроме edge) обслуживают любой ящик и взаимно заменяют друг друга; клиенты подключаются к общему виртуальному адресу. Данные размещены на трёх ВМ данных: на двух — PostgreSQL (primary и синхронная реплика), на третьей — монитор, который выбирает primary и не даёт появиться двум primary. На всех трёх ВМ работают узлы SeaweedFS (тела писем с двумя копиями на разных ВМ; метаданные файловой системы SeaweedFS хранятся в том же PostgreSQL) и узлы кластера OpenBao.

Схема: deploy-small.svg — Малый Enterprise: 2 узла и 3 ВМ данных

**Таблица: Состав схемы «Малый Enterprise»**

| Компонент | Кол-во | Назначение | Ограничения |
|---|---|---|---|
| Узел, пресет mailbox (4 vCPU, 8 GB RAM) | 2 | Все роли; Rspamd на каждом узле | Каждый узел должен выдерживать всю нагрузку один |
| Виртуальный адрес | 1 | Вход клиентов и почты: keepalived или балансировщик заказчика | keepalived — оба узла в одном сегменте сети |
| PostgreSQL primary и standby (4 vCPU, 16 GB RAM, NVMe) | 2 | Метаданные; синхронная репликация | Один кандидат синхронной реплики (исключение из п. 3.1): при отказе standby запись продолжается без синхронной реплики до его возврата |
| Монитор pg_auto_failover | 1 | Выбор primary, свидетель | Без монитора автоматическое переключение не выполняется |
| SeaweedFS: master, volume, filer, шлюз S3 | 3 | Тела писем, индексы; две копии объекта | Ёмкость — суммарный диск трёх ВМ, делённый на 2 |
| OpenBao | 3 | Секреты, кластер Raft | Кворум — 2 из 3 |
| Узлы edge | 0–2 | Приём из интернета в DMZ (п. 2.6) | По требованию сегментации сети |

Поведение при отказах:

- отказ узла mailbox — клиенты переподключаются ко второму узлу, письма не теряются (ответ 250 — только после записи);
- отказ ВМ с primary — переключение ≤ 30 с, на время переключения SMTP отвечает 4xx;
- отказ любой одной ВМ данных — SeaweedFS и OpenBao продолжают работу на двух оставшихся;
- одновременный отказ двух ВМ данных — недоступность до восстановления.

## З.3. Enterprise-ВМ

Для организаций от 1 000 ящиков. Роли разнесены по пресетам: edge в DMZ принимает почту из интернета, transport обрабатывает очереди и отправку с фиксированных адресов, access обслуживает клиентов, backend строит индексы и выполняет фоновые задачи. Каждая группа масштабируется добавлением ВМ. Слой данных — кластеры PostgreSQL, SeaweedFS и OpenBao — настраивает и сопровождает заказчик по требованиям п. 3.1.

Схема: deploy-entvm.svg — Enterprise-ВМ

**Таблица: Состав схемы Enterprise-ВМ**

| Компонент | Кол-во | Назначение | Ограничения |
|---|---|---|---|
| Узлы edge | ≥ 2 | Приём 25 в DMZ, без доступа к БД и BLOB | Передача на transport в той же сессии; недоступность transport — 4xx |
| Узлы transport | ≥ 2 | smtp-in, smtp-out, egress-IP | Адреса egress — в SPF и PTR |
| Узлы access | ≥ 2, по нагрузке | submission, IMAP, JMAP, DAV, Admin API | Долгоживущие соединения — корректное завершение при остановке |
| Узлы backend | ≥ 2 | Поиск, индексация, обслуживание | Лидер обслуживания — по аренде, переезжает автоматически |
| L4-балансировщик | 2 | Распределение клиентов, PROXY v2 | Таймауты не меньше времени IDLE |
| PgBouncer | на узел или пара | Пул соединений к СУБД | Соединение сигналов — мимо него (п. 2.8) |
| Кластер PostgreSQL | primary + ≥ 2 кандидата | Метаданные, RPO = 0, RTO ≤ 30 с | До 10⁵–10⁶ ящиков на кластер, далее — шарды (п. 3.6) |
| SeaweedFS | 3 master, ≥ 3 volume, ≥ 2 filer | Тела писем, индексы | Шлюзы S3 — за балансировщиком |
| OpenBao | 3 | Секреты | Кворум — 2 из 3 |
| Rspamd | ≥ 2 | Антиспам по Milter | Недоступность — по политике Milter (п. 4.1) |

Поведение при отказах: отказ узла любой роли — нагрузку принимают узлы той же роли; переключение СУБД — ≤ 30 с с временными отказами; отказ узла хранилищ — по их кворуму.

## З.4. Enterprise-K8s

Для динамической нагрузки и заказчиков с платформой Kubernetes. Каждая группа ролей — отдельный Deployment; число подов меняет HPA по загрузке CPU (по числу соединений — по выбору заказчика), размеры памяти подбираются по рекомендациям VPA. Узлы edge остаются ВМ в DMZ вне кластера. PostgreSQL — оператор CloudNativePG, хранилища — Helm-чарты.

Схема: deploy-entk8s.svg — Enterprise-K8s

**Таблица: Состав схемы Enterprise-K8s**

| Компонент | Кол-во | Назначение | Ограничения |
|---|---|---|---|
| Deployment transport, access, backend | ≥ 2 пода каждый | Роли по пресетам | PodDisruptionBudget, anti-affinity по узлам кластера |
| HPA | на Deployment | Масштабирование по CPU; по соединениям — опция | Окно стабилизации при сжатии; по соединениям — нужен prometheus-adapter |
| VPA | режим рекомендаций | Размеры requests и limits | Автоматическое применение не используется |
| Service LoadBalancer | 1 на протокол | Вход клиентов | Адрес клиента — externalTrafficPolicy: Local или PROXY v2 |
| CloudNativePG | primary + реплики | Метаданные, Pooler | Требования п. 3.1 |
| SeaweedFS, OpenBao, Rspamd | по чартам | Хранилища, секреты, антиспам | OpenBao — вход Kubernetes auth |
| Узлы edge | ≥ 2 ВМ | DMZ вне кластера | Как в З.3 |

Поведение при отказах: Kubernetes перезапускает поды и переносит их с отказавших узлов кластера; остальное — как в З.3.

## З.5. DR active-passive

Резервная площадка на случай потери основной. На площадке A работает полная схема З.3 или З.4. На площадке B данные непрерывно копируются асинхронно: реплика PostgreSQL, копия BLOB средствами SeaweedFS (filer.sync), копия секретов. Узлы The Post на B установлены и настроены, но остановлены: они не могут работать с репликой только для чтения. При потере площадки A администратор выполняет процедуру переключения: повышает PostgreSQL и SeaweedFS на B, запускает узлы, переключает DNS и MX.

Схема: deploy-dr.svg — DR active-passive

**Таблица: Состав схемы DR active-passive**

| Компонент | Площадка A | Площадка B | Ограничения |
|---|---|---|---|
| Узлы The Post | Полный набор | Установлены, остановлены | Запуск — при переключении |
| PostgreSQL | primary + синхронные реплики | Асинхронная реплика или реплика-кластер | RPO — отставание репликации (секунды) |
| SeaweedFS | Основной кластер | Копия (filer.sync) | RPO по телам писем — отставание; с модулем «Геораспределение» доставка подтверждается после репликации |
| OpenBao | Кластер | Копия (снимки Raft) | Изменения секретов между снимками — вручную |
| DNS, MX | Основные записи | Резервные записи | TTL записей определяет время переключения клиентов |

Поведение при отказах: потеря площадки A — переключение по процедуре, RTO — минуты (длительность процедуры), RPO — отставание асинхронной репликации.

## З.6. Метро-кластер

Две площадки на расстоянии до ~100 км (задержка ≤ 5 мс) работают как один кластер. На каждой площадке есть узлы всех ролей, синхронная реплика PostgreSQL находится на другой площадке, копии BLOB SeaweedFS размещаются на обеих. Третья площадка (свидетель) содержит только монитор СУБД, master SeaweedFS и узел OpenBao: без неё при разрыве связи между A и B каждая сторона могла бы объявить себя главной.

Схема: deploy-metro.svg — Метро-кластер

**Таблица: Состав схемы «Метро-кластер»**

| Компонент | Площадка A | Площадка B | Площадка C | Ограничения |
|---|---|---|---|---|
| Узлы The Post | Каждая роль ≥ 1 | Каждая роль ≥ 1 | — | Ёмкость каждой площадки — вся нагрузка |
| PostgreSQL | primary + асинхронный кандидат | синхронная реплика + асинхронный кандидат | монитор | Синхронная реплика — на другой площадке |
| SeaweedFS | master, volume | master, volume | master | Копия объекта на другой площадке (replication 100) |
| OpenBao | узел Raft | узел Raft | узел Raft | Кворум — 2 из 3 площадок |
| Вход клиентов, MX, egress | Адреса площадки | Адреса площадки | — | Записи MX и SPF — обеих площадок |

Поведение при отказах: потеря площадки — автоматическое переключение СУБД ≤ 30 с, RPO = 0, клиенты переподключаются к узлам другой площадки; потеря свидетеля — работа продолжается, автоматическое переключение недоступно до его возврата.

## З.7. Гео active-active (модуль «Геораспределение»)

Площадки на большом расстоянии, каждая обслуживает свою часть ящиков. У каждого ящика есть домашняя площадка — площадка шарда, на котором он размещён; все записи ящика выполняются только там. Шарды площадки A имеют primary на A и асинхронную реплику на B, и наоборот. Каталог (шард 0) имеет primary на одной площадке и реплику на другой; читается локально. Если клиент ящика A подключился к площадке B, она перенаправляет его (JMAP, DAV, Admin API), проксирует сессию (IMAP, submission) или пересылает письмо (SMTP) на площадку A (п. 2.9).

Схема: deploy-geo.svg — Гео active-active

**Таблица: Состав схемы «Гео active-active»**

| Компонент | На каждой площадке | Ограничения |
|---|---|---|
| Узлы The Post | Полный набор ролей, лидер обслуживания — свой | Межплощадочный трафик — перенаправленные сессии и пересланные письма |
| Шарды площадки | primary | Ящики с домашней площадкой; реплика — на другой площадке, асинхронно |
| Реплики шардов другой площадки | Асинхронные | Повышаются при потере той площадки; RPO — отставание |
| Шард 0 (каталог) | primary на одной, реплика на другой | Запись в каталог (создание ящиков, изменение доменов) — только при доступности primary |
| S3 площадки | Свой кластер, двусторонняя асинхронная репликация | Объект, ещё не дошедший до площадки, читается с соседней |
| OpenBao | Кластер площадки | Общие ключи (DKIM, SRS) — на обеих площадках |

Поведение при отказах: разрыв связи — каждая площадка продолжает обслуживать свои ящики, ящики другой площадки недоступны; потеря площадки — её ящики доступны после повышения реплик на другой площадке (по процедуре или автоматически со свидетелем), RPO — отставание асинхронной репликации.
