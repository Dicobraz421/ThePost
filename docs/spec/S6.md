# 6. Сеть, безопасность и эксплуатация

## 6.1. Балансировка нагрузки

Собственный прокси-слой не входит в продукт. В профиле SMB балансировка не требуется; в Enterprise используется L4-балансировщик заказчика. Требования к балансировщику:

- работа на уровне L4 (TCP) без терминации TLS;
- передача адреса клиента — PROXY protocol v2 или externalTrafficPolicy: Local;
- проверка доступности по ролям — HTTP /healthz/ready и /healthz/live каждого узла;
- таймаут простоя соединения — не менее 30 минут (IMAP IDLE, JMAP push);
- вывод узла из пула по проверке доступности при остановке (drain).

**Таблица: Рекомендуемые варианты балансировки**

| Среда | Рекомендация | Примечание |
|---|---|---|
| Kubernetes на собственном оборудовании | MetalLB в режиме BGP с ECMP | Режим L2 обеспечивает только переключение при отказе, без распределения нагрузки |
| Виртуальные машины | HAProxy + keepalived в режиме TCP | Пара узлов с общим VIP |
| Имеющийся аппаратный или облачный балансировщик | Режим L4, PROXY v2 | Проверить поддержку PROXY v2 и таймауты простоя |

Публикация портов:

- приём почты (25) — по записям MX в DNS: отдельный VIP или прямая адресация узлов edge (п. 2.6) или smtp-in несколькими записями MX;
- клиентский доступ (465, 587, 993, 995, 443) — через балансировщик;
- исходящая почта — с фиксированных egress-IP (выделенные узлы smtp-out или egress-gateway), согласованных с PTR и SPF.

**Обоснование.** STARTTLS начинается внутри протокола (25, 587, 143), поэтому TLS терминирует ядро; проверка подлинности почты также выполняется ядром. Узлы без состояния не требуют привязки клиента к узлу, поэтому достаточно L4 — та же модель рекомендуется Microsoft для Exchange. Повторные попытки отправителей SMTP обеспечивают распределение приёма по записям MX без балансировщика.

## 6.2. Шифрование и TLS

- TLS реализуется ядром (rustls): клиентский доступ — TLS 1.3 (TLS 1.2 — по настройке для устаревших клиентов); обмен между MTA — TLS 1.2+, оппортунистический STARTTLS, обязательный TLS по политикам MTA-STS и DANE;
- сертификаты — встроенный клиент ACME (SMB) либо файлы или секреты Kubernetes с перечитыванием без перезапуска (Enterprise, например cert-manager);
- шифрование содержимого S/MIME и OpenPGP выполняется клиентами; сервер хранит и передаёт зашифрованные письма без изменений;
- внутренние каналы (PostgreSQL, Valkey, S3, хранилище секретов, обмен между узлами, служебный HTTP `/metrics` и `/healthz`) — только TLS; открытый канал допускается лишь в профиле разработки по явной настройке, с предупреждением в журнале (решение 2026-10-30);
- шифрование хранимых данных — средствами хранилищ (PostgreSQL, SeaweedFS, шифрование дисков), при необходимости с раздельными ключами по tenant.

**Обоснование.** Обязательный TLS 1.3 между MTA сделал бы невозможной доставку от части внешних серверов; защита канала между MTA обеспечивается политиками MTA-STS и DANE.

## 6.3. Защита от перебора и злоупотреблений

Ядро ограничивает частоту соединений и попыток аутентификации по IP-адресу, подсети и учётной записи; временно блокирует источники при превышении порогов; ограничивает частоту отправки для учётной записи (защита от рассылок со скомпрометированных ящиков). Защита от DDoS на сетевом уровне — средствами периметра заказчика.

## 6.4. Наблюдаемость

- метрики в формате Prometheus на /metrics каждого узла: очереди, задержки по протоколам и операциям, соединения, пулы БД, кэши, индексация, GC, миграция, шина событий;
- структурированные логи (JSON в stdout → journald/syslog); трейсы — опционально с экспортом по OTLP (OpenTelemetry);
- проверки доступности — /healthz/live, /healthz/ready;
- дашборды, оповещения и хранилища метрик не входят в продукт.

## 6.5. Доступность

Целевые показатели Enterprise: SLA 99,95 % (цель — 99,99 %); отказ узла приложения — переподключение клиентов не более 30 с без потери принятых писем; отказ primary СУБД — RTO ≤ 30 с, RPO = 0 (при выполнении требований п. 3.1). Для SMB SLA не нормируется.

## 6.6. Обновление

Обновление выполняется последовательно по узлам (rolling) без остановки сервиса. Миграции схемы БД совместимы с предыдущей версией (N−1): расширение схемы — до обновления узлов, удаление устаревших элементов — в следующем выпуске.

## 6.7. Управление секретами

Секреты хранятся только во внешнем хранилище секретов с API HashiCorp Vault; собственное хранилище в продукт не входит. Эталон — OpenBao (MPL-2.0, Linux Foundation); при наличии у заказчика OpenBao или HashiCorp Vault используется оно.

- через хранилище передаются: учётные данные PostgreSQL (основная БД и шарды), ключи S3, пароль Valkey, закрытые ключи DKIM и учётной записи ACME, ключи подписи токенов, секреты LDAP, OIDC и внешних систем; закрытые ключи TLS — из хранилища, если администратор не выбрал файлы или секреты Kubernetes (п. 6.2);
- в config.yaml и таблицах БД — только ссылки на секреты (п. 5.5);
- механизмы хранилища: KV v2; динамические учётные данные PostgreSQL (database secrets engine) — по настройке; аренды (lease) продлеваются узлом;
- вход узла: Kubernetes auth (Enterprise-K8s), сертификат TLS узла, AppRole с secret_id из учётных данных systemd (ВМ);
- для продукта в хранилище выделяются отдельный путь (mount) KV, политика с минимальными правами на чтение и отдельная роль входа для каждого пресета узла;
- секреты читаются при запуске и при перечитывании конфигурации;
- распечатывание OpenBao эталонной установки — автоматическое: ключ из TPM, PKCS#11 или KMS; при их отсутствии — ключ в файле на том же сервере с предупреждением thepost doctor; ручной ввод ключа — по настройке.

**Обоснование.** Шифрование, распечатывание, политики доступа и аудит доступа к секретам — отдельный продукт с высоким риском ошибок безопасности; готовое хранилище закрывает их, а совместимость с API Vault позволяет использовать имеющуюся у заказчика инфраструктуру без дублирования.
