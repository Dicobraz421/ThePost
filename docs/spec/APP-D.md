# Приложение Д. Тестовый стенд и методика нагрузочных испытаний

## Д.1. Назначение стенда

- подтверждение критериев приёмки (Д.7) для профилей SMB, Enterprise-ВМ и Enterprise-K8s;
- проверка инвариантов хранения (п. 3.4, 3.5) при отказах и сетевых сбоях;
- получение данных для сайзинга (раздел 8).

## Д.2. Состав стенда

## Д.3. Модель нагрузки

Модель задаётся на одного пользователя в рабочие сутки.

**Таблица: Модель нагрузки**

| Параметр | Значение |
|---|---|
| Входящие письма | 120 |
| Исходящие письма | 30, из них 50 % — внутренним адресатам |
| Средний размер письма | 75 KB |
| Письма с вложениями | 20 %, средний размер вложения — 500 KB |
| Внутренние дубли MIME-частей | 30 % |
| Подключены одновременно в пиковый час | 60 % пользователей |
| Устройств на пользователя | 1,5 (IMAP IDLE или JMAP push) |
| Пиковый коэффициент | ×2 к среднечасовой нагрузке |
| Поисковые запросы | 10 |
| Изменения флагов и перемещения | 200 |
| Календарные операции | 15, из них 3 приглашения |

Наполнение перед испытаниями выполняется через Admin API импорта (п. 5.2) из синтетического корпуса и публичного корпуса Enron (реалистичный текст для поиска):

- Enterprise — 2 000 ящиков по 10 000 писем (≈ 20 млн писем, ≈ 1,5 TB до дедупликации) и 5 общих ящиков по 1 млн писем;
- SMB — 1 000 ящиков по 1 500 писем (≈ 110 GB).

## Д.4. Инструменты

- imaptest — сценарии IMAP (SELECT, FETCH, IDLE, STORE, APPEND) с профилями клиентов;
- smtp-source и smtp-sink (Postfix) — входящий поток и приёмник исходящей почты;
- k6 — JMAP, push (WebSocket), CalDAV, CardDAV, Admin API;
- toxiproxy, tc netem — задержки, потери и обрывы между ядром и PostgreSQL / S3;
- отказы — остановка процесса (kill -9), удаление пода, переключение primary PostgreSQL, выключение узла SeaweedFS, разрыв сети между узлами;
- собственный генератор нагрузки — в дорожной карте (приложение Е).

## Д.5. Эмуляция масштаба настройкой пороговых значений

Стенд меньше промышленной инсталляции, поэтому пороговые значения уменьшаются: механизмы, которые в эксплуатации срабатывают редко или только на большом масштабе, должны срабатывать в течение испытания. Требование к ядру: все параметры задаются в config.yaml и применяются без перезапуска (п. 5.5).

**Таблица: Пороговые значения для стенда**

| Параметр | Значение по умолчанию | Значение на стенде | Что проверяется |
|---|---|---|---|
| HPA: целевая загрузка CPU | 70 % | 20 % | Масштабирование ролей при малой нагрузке |
| Срок хранения корзины | 30 сут | 15 мин | Переход к окончательному удалению, работа GC |
| Окно W | ≥ окна PITR (14 сут) | 30 мин | Инвариант W при восстановлении PITR |
| Период ожидания GC | 24 ч | 5 мин | Гонка GC и дедупликации, поколения объектов |
| Интервал поиска «сирот» | 24 ч | 2 мин | Очистка после обрыва S3 во время загрузки |
| Пул соединений узла / PgBouncer | 20 / 200 | 3 / 20 | Исчерпание пула, очереди запросов |
| Кэш moka / NVMe-кэш узла | 2 GB / 300 GB | 16 MB / 2 GB | Промахи кэша, нагрузка на S3 |
| Интервал коммита индекса | 30 с | 5 с | Число сегментов, слияния, задержка индексации |
| Кэш индексов на узле search | 200 GB | 1 GB | Холодная загрузка индексов из S3 |
| Повторы очереди SMTP | 15 мин … 5 сут | 1 мин … 30 мин | Повторы, уведомления о недоставке (DSN) |
| Rate limit: соединений с IP | 50 | 5 | Защита от перебора |
| Квота ящика | 50 GB | 50 MB | Поведение при превышении квоты |
| Обнаружение отказа HA СУБД (интервал проверки / тайм-аут) | по умолчанию средства HA | минимальные для средства | Фактический RTO, поведение узлов при переключении |
| Ограничение мигратора | 200 MB/s | 1 и 50 MB/s | Перенос BLOB под нагрузкой, расчёт ETA |
| Ограничение переноса ящиков | 50 MB/s | 1 MB/s | Перенос между шардами под нагрузкой |
| Таймаут простоя балансировщика | 30 мин | 2 мин | Переподключение IMAP IDLE и push |

## Д.6. Сценарии испытаний

**Таблица: Сценарии испытаний**

| Сценарий | Содержание | Длительность |
|---|---|---|
| Базовый | Номинальная модель нагрузки | 2 ч |
| Пиковый | Нагрузка ×2 к номинальной | 1 ч |
| Стресс | Рост нагрузки до нарушения критериев; фиксируются точка насыщения и узкое место | До отказа |
| Длительный | Номинальная нагрузка | 72 ч |
| Отказы | Остановка primary PostgreSQL, узла SeaweedFS, узла приложения; разрыв сети ядро — S3 во время загрузки | По сценарию |
| Миграция бэкенда | Перенос BLOB и индексов «локальный диск → S3» под номинальной нагрузкой | До завершения |
| Перенос ящиков | Перенос 100 ящиков между шардами под нагрузкой | До завершения |
| Восстановление | PITR на точку T при работающем GC, сверка thepost verify | По сценарию |
| Обновление | Rolling-обновление N → N+1 под нагрузкой | По сценарию |

Сценарии «Миграция бэкенда» и «Перенос ящиков» выполняются при наличии соответствующих модулей (п. 1.3).

## Д.7. Критерии приёмки

**Таблица: Критерии приёмки**

| Показатель | Критерий |
|---|---|
| JMAP Email/query, Email/get, p95 | < 200 мс |
| IMAP SELECT папки 10 тыс. писем, p95 | < 100 мс |
| Приём SMTP до ответа 250, p95 | < 500 мс |
| Внутренняя доставка до появления в ящике, p95 | < 5 с |
| Задержка сигнала между узлами (фиксация → уведомление IMAP IDLE / JMAP push), p99 | < 1 с |
| Доля времени фиксации на primary, занятая NOTIFY | ≤ 5 % (иначе — пересмотр транспорта сигналов, п. 2.8) |
| Полнотекстовый поиск, ящик 100 тыс. писем, p95 | < 1 с |
| Полнотекстовый поиск, общий ящик 1 млн писем, p95 | < 3 с |
| Задержка индексации, p95 | < 60 с |
| Холодная загрузка индекса ящика 100 тыс. писем | < 10 с |
| Переключение primary PostgreSQL | RTO ≤ 30 с, RPO = 0 |
| Отказ узла приложения | Переподключение клиентов ≤ 30 с, без потери принятых писем |
| «Сироты» после цикла GC | 0 |
| Потерянные объекты после PITR (thepost verify) | 0 |
| Длительный тест 72 ч | Рост памяти ≤ 10 %, деградация p95 ≤ 20 % |
| Память на простаивающее соединение IMAP IDLE или JMAP push | ≤ 64 KB |
| Поведение под нагрузкой ×3 к номинальной | Узел не завершается аварийно; принятые письма не теряются; отказы — только 4xx (п. 6.3) |
| SMB, 1 000 пользователей | Все критерии на 4 vCPU / 8 GB |
