# 2. Архитектура

## 2.1. Модульный монолит с ролями

Ядро — модульный монолит: единая кодовая база и единый бинарный файл, функции которого разделены на роли. Набор ролей узла задаётся в config.yaml. В профиле SMB все роли работают в одном процессе; в Enterprise каждая роль развёртывается и масштабируется отдельно.

**Таблица: Роли ядра**

| Роль | Назначение | Состояние |
|---|---|---|
| smtp-in | Приём почты (25); проверка SPF, DKIM, DMARC, ARC; вызов Milter; выполнение Sieve; доставка. Режим edge — п. 2.6 | Без состояния; в режиме edge — локальная очередь |
| submission | Отправка клиентами (587, 465) с аутентификацией SASL; ограничение частоты отправки | Без состояния |
| smtp-out | Обработка очереди исходящей почты, DKIM-подпись, MTA-STS, DANE, повторы, DSN | Без состояния, очередь в PostgreSQL |
| imap | IMAP4rev2; POP3 (выключен по умолчанию) | Без состояния, долгоживущие соединения |
| jmap | JMAP Core, Mail, Submission, Push, Sieve, Calendars, Contacts, Tasks | Без состояния, долгоживущие соединения push |
| dav | CalDAV, CardDAV, scheduling, free/busy, GAL | Без состояния |
| admin | Admin REST API, экспорт и импорт; операции модулей | Без состояния |
| search | Выполнение поисковых запросов по индексам ящиков | Кэш индексов на NVMe (производные данные) |
| indexer | Построение индексов; извлечение текста вложений в изолированных подпроцессах (п. 2.7) | Без состояния, задания в PostgreSQL |
| maintenance | GC, поиск «сирот», verify; фоновые задания модулей (миграция бэкенда, перенос ящиков) | Без состояния, лидер — по лизе в PostgreSQL |

Источник истины — PostgreSQL и BLOB-хранилище; любой узел обслуживает любой ящик. Уведомления об изменениях (JMAP push, IMAP IDLE) между узлами передаются сигналами (п. 2.8): в кластере — через PostgreSQL LISTEN/NOTIFY, в одном процессе — каналом в памяти.

Слой данных — PostgreSQL, BLOB-хранилище, хранилище секретов — внешний и не является ролью продукта. В профиле SMB эталонная установка размещает PostgreSQL и OpenBao на той же ВМ (п. 1.2).

Набор ролей узла задаётся параметром `roles` в config.yaml: пресетами, отдельными ролями или их сочетанием.

**Таблица: Пресеты ролей**

| Пресет | Роли | Размещение |
|---|---|---|
| all | Все роли | SMB: одна ВМ |
| edge | smtp-in в режиме edge (п. 2.6) | DMZ |
| transport | smtp-in, smtp-out | Внутренний контур; фиксированные egress-IP |
| access | submission, imap, jmap, dav, admin | Внутренний контур, за L4-балансировщиком |
| backend | search, indexer, maintenance | Внутренний контур |
| mailbox | transport + access + backend | Минимальный Enterprise: узлы edge и mailbox |

Пресеты mailbox и edge соответствуют ролям Mailbox и Edge Transport Microsoft Exchange; пресеты transport, access и backend применяются для раздельного масштабирования.

**Обоснование.** Модульный монолит сохраняет преимущества микросервисов — изоляцию сбоев на уровне процессов, независимое масштабирование ролей, раздельные лимиты ресурсов — без их издержек: нет сетевых вызовов между сервисами, одна версия и один цикл выпуска, один артефакт для всех профилей. Требование единого бинарного файла выполняется без противоречий.

## 2.2. Среда выполнения

Целевые платформы — Linux x86_64 и AArch64. Сборка под другие ОС не выполняется и не тестируется. Доступ к ОС (сеть, диск, сигналы, распределение памяти) изолирован в отдельном модуле (crate); логика протоколов не содержит системных вызовов и тестируется без ОС.

Асинхронный рантайм — Tokio (epoll). Использование io_uring не является требованием и допускается после стабилизации его поддержки в рантайме; изменения затрагивают только системный модуль.

**Обоснование.** Одна платформа сокращает матрицу сборки и тестирования и позволяет использовать механизмы Linux (seccomp для sandbox, cgroups). Изоляция системного кода обеспечивает тестируемость логики протоколов и локализует изменения при смене рантайма. Переносимость для потребителя обеспечивается OCI-образом.

## 2.3. Варианты развёртывания Enterprise

Поддерживаются два равноправных варианта:

- Enterprise-ВМ — бинарный файл на N виртуальных машинах под systemd за L4-балансировщиком; масштабирование добавлением ВМ;
- Enterprise-K8s — роли как отдельные Deployment в Kubernetes (Helm-чарт), HPA по CPU (по числу соединений — по выбору заказчика, через prometheus-adapter) с окном стабилизации при сжатии, PodDisruptionBudget, anti-affinity по узлам, rolling-обновление; память — requests и limits, размеры — по рекомендациям VPA.

**Обоснование.** HPA по памяти не используется: память узла занята кэшами до лимита (п. 2.7) и после пика не освобождается — масштабирование по ней только наращивало бы число подов. Окно стабилизации исключает разрыв долгоживущих соединений (IMAP IDLE, JMAP push) при колебаниях нагрузки. Kubernetes оправдан при динамической нагрузке: автоматическое масштабирование, самовосстановление, обновление без простоя. Обязательный Kubernetes стал бы главным источником сложности для заказчиков без собственной платформы; вариант на ВМ по модели эксплуатации соответствует серверам Exchange, но без состояния на узлах.

## 2.5. Точки расширения

Дополнительные модули (п. 1.3) подключаются только через точки расширения ядра:

- интерфейсы (крейт tp-contracts): BlobStore, Directory, SearchIndex, EventSink; модуль добавляет реализацию, не изменяя ядро;
- реестр ролей, capability JMAP и маршрутов Admin API: модуль регистрирует собственные роли, capability и маршруты;
- события ядра — доставка, отправка, изменение флагов, перемещение, удаление в корзину, окончательное удаление, создание и удаление ящика; событие записывается в таблицу outbox в той же транзакции, что и изменение; подписчики (индексатор, модули) читают события с сохранением позиции; доставка не менее одного раза, порядок — в пределах ящика;
- точки принятия решений — синхронные проверки, в которых модуль может запретить или дополнить операцию: перед окончательным удалением (Legal Hold, политики хранения), при доставке и отправке (журналирование); при отсутствии модулей проверка не выполняет действий;
- данные модуля — в отдельной схеме PostgreSQL (`mod_<имя>`) с собственной последовательностью миграций; требования совместимости — п. 6.6;
- конфигурация модуля — секция `modules.<имя>` в config.yaml, описанная в JSON Schema (п. 5.5).

**Обоснование.** События в outbox в одной транзакции с изменением гарантируют, что модуль не пропустит изменение и не увидит неподтверждённое. Отдельная схема БД изолирует данные модуля и позволяет отключить или удалить модуль без изменения схемы ядра.

## 2.6. Пограничный узел (edge)

Узел с пресетом edge размещается в DMZ и принимает почту из интернета:

- узел не имеет доступа к PostgreSQL и BLOB-хранилищу; их адреса в конфигурации узла отсутствуют;
- выполняются приём на порту 25, TLS, проверки SPF, DKIM, DMARC, ARC, вызов Milter, ограничение частоты, проверка получателя;
- узел не имеет очереди и состояния: письмо после проверок передаётся в той же сессии по SMTP с взаимной аутентификацией TLS на узел transport; ответ 250 отправителю — только после того, как transport сохранил письмо в PostgreSQL и BLOB-хранилище; при недоступности внутреннего контура — временный отказ 4xx, повторы выполняет отправитель (RFC 5321); выполнение Sieve и доставка — на узлах transport;
- проверка получателей выполняется по реплике списка адресов: узлы transport передают на edge подписанный снимок адресов и доменов (без иных атрибутов учётных записей) и инкрементальные обновления; соединения инициируются из внутреннего контура; при недоступности внутреннего контура edge работает по последнему снимку;
- секреты узла (закрытый ключ TLS для приёма, сертификат и ключ канала к transport) узел читает из хранилища секретов напрямую, как остальные узлы (п. 6.7): отдельная роль входа и политика только на чтение пути edge; вход — по сертификату узла или AppRole с secret_id из учётных данных systemd, токены с коротким сроком действия; доступ к API хранилища из DMZ разрешается межсетевым экраном только с адресов узлов edge;
- исходящая почта отправляется узлами smtp-out напрямую с egress-IP либо через edge в режиме ретрансляции (настройка);
- приём распределяется между несколькими узлами edge записями MX; отказ узла не приводит к потере писем.

Вместо узлов edge перед продуктом может работать внешний MTA заказчика (шлюз — доверенный источник, п. 4.1), а исходящая почта — уходить через внешний промежуточный узел (smart host). Внешний MTA допускается только на периметре — до smtp-in и после smtp-out: приём для доменов организации, Milter, правила потока (модуль), Sieve, доставка в ящик и очередь исходящей почты всегда выполняются продуктом. Функции транспорта, которых нет в ядре (приложение Ж), выполняет внешний MTA на периметре.

**Обоснование.** Требования сегментации сети не допускают доступа узла DMZ к хранилищам данных. Модель соответствует роли Edge Transport Microsoft Exchange (синхронизация получателей — аналог EdgeSync). Сквозная передача без локальной очереди (как проверка до постановки в очередь в Postfix) делает узел edge узлом без состояния и исключает потерю принятых писем; цена — задержка ответа на один внутренний переход. Сквозная передача уже требует соединения из DMZ к transport, поэтому прямое чтение секретов edge из хранилища не расширяет модель угроз существенно: при компрометации edge доступны только его собственные секреты, а каждое обращение фиксируется в журнале аудита хранилища; собственный протокол доставки секретов не требуется.

## 2.7. Ресурсы и изоляция ролей

- невключённая роль не создаёт пулов соединений, кэшей, потоков и слушающих портов; страницы кода невключённых ролей не загружаются в резидентную память;
- лимиты кэшей и пулов задаются по ролям; значения по умолчанию рассчитываются от ресурсов узла с учётом набора ролей;
- резидентная память (RSS) узла с одной ролью без нагрузки — не более 64 MB (уточняется на стенде, приложение Д);
- извлечение текста вложений выполняется в пуле отдельных подпроцессов (подкоманда того же бинарного файла): seccomp, лимиты памяти и CPU (rlimit, cgroups), таймаут, без доступа к сети и записи на диск; аварийное завершение подпроцесса не влияет на основной процесс, документ отмечается как неизвлечённый, подпроцесс перезапускается;
- разбор MIME выполняется в основном процессе (библиотека mail-parser, безопасный по памяти код).
- ресурсы узла определяются по лимитам cgroups (контейнер, под, служба systemd), а не по ресурсам хоста, и перечитываются без перезапуска; при изменении лимитов (VPA, горячее добавление памяти и CPU гипервизором) пересчитываются размеры пулов, кэшей и пороги п. 6.3.

Минимальные привилегии:

- процесс работает от непривилегированной учётной записи; порты ниже 1024 — через активацию сокетов systemd или CAP_NET_BIND_SERVICE; иные capabilities не используются;
- для каждой роли действуют собственный профиль seccomp и ограничения Landlock: доступны только нужные роли каталоги и системные вызовы; узел edge не имеет доступа к файловой системе, кроме конфигурации и файла учётных данных входа в хранилище секретов (п. 2.6);
- эталонная служба systemd: NoNewPrivileges, ProtectSystem=strict, ProtectHome, PrivateTmp, PrivateDevices, MemoryDenyWriteExecute, RestrictAddressFamilies, SystemCallFilter, пустой CapabilityBoundingSet (кроме привязки портов);
- Kubernetes: runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation: false, удаление всех capabilities, профиль seccomp RuntimeDefault и собственный;
- PostgreSQL: отдельные учётные записи по ролям узла с минимальными правами (п. 3.1); учётная запись приложения не является владельцем схемы и не имеет BYPASSRLS.

**Обоснование.** Размер бинарного файла не определяет потребление памяти: код загружается по требованию, а RSS формируют кэши, пулы и буферы соединений. Тот же подход применяется в Grafana Mimir и Loki. Отдельный подпроцесс для разбора недоверенных форматов (PDF, Office) исключает влияние уязвимостей и сбоев парсеров на работу узла, в том числе в профиле SMB, где все роли работают в одном процессе. Минимальные привилегии каждой роли ограничивают последствия ошибок, которые не предотвращает безопасность по памяти: логических ошибок и уязвимостей зависимостей.

## 2.8. Взаимодействие компонентов

Правила (решение 2026-11-01):

1. правда хранится только в PostgreSQL и BLOB-хранилище; средства взаимодействия не держат состояния, потеря которого нарушает корректность;
2. сигнал об изменении отправляется только после фиксации изменения;
3. получатель при запуске и после переподключения сверяется с хранилищем, далее работает по сигналам;
4. периодический опрос хранилищ и очередей запрещён; таймеры допускаются только из закрытого списка (ниже).

**Таблица: Виды взаимодействия**

| Вид | Гарантия | Примеры | Один процесс | Кластер |
|---|---|---|---|---|
| Сигнал — «изменилось X» | Не более одного раза; при потере — сверка по ModSeq или позиции | IMAP IDLE, JMAP push, пополнение очереди, новые события в разделе журнала, изменение конфигурации и состава кластера | Канал в памяти | PostgreSQL LISTEN/NOTIFY |
| Событие — журнал изменений (outbox, п. 2.5) | Не менее одного раза, порядок в пределах ящика | Индексация, модули, журнал доставки | Таблица PostgreSQL | Таблица PostgreSQL; читатель раздела — по аренде |
| Задание — выполнить один раз | Один исполнитель, повтор при сбое | Отправка письма, фоновые работы | Таблица PostgreSQL с захватом записи | То же |
| Запрос — синхронный вызов роли на другом узле | Ответ, «занят» или истечение срока | Поиск по индексу на узле-владельце, состояние узлов для администрирования | Вызов функции | HTTPS/2 с взаимным TLS между узлами |

Запись события или задания и последующий сигнал образуют связку: читатель журнала и исполнитель очереди ожидают сигнала, по сигналу дочитывают таблицу до конца и снова ожидают; потерянный сигнал не нарушает корректность (правило 3).

Сигналы:

- тема сигнала содержит организацию: `<tenant>/<ящик>`, `<tenant>/queue/<вид>`, `log/<раздел>`, `system/config`, `system/members`; подписка на тему другой организации запрещена;
- публикатор узла отправляет NOTIFY отдельной короткой транзакцией после фиксации изменения, а не внутри почтовой транзакции; пока предыдущая отправка не завершена, новые сигналы накапливаются и уходят одной пачкой следующей отправкой — склейка зависит от нагрузки, таймер не используется;
- у каждого узла по одному прямому соединению-слушателю с primary каждого шарда (п. 3.6; в базовой поставке шард один) мимо PgBouncer в режиме transaction; primary определяется так же, как для остальных соединений (п. 3.1);
- фильтрация по интересам выполняется на узле; у подписчика ограниченный буфер, при переполнении сигналы отбрасываются и подписчик получает признак «сверка», по которому сверяется с хранилищем.

Запросы и состав кластера:

- узел при запуске регистрирует в PostgreSQL свой идентификатор, роли и адрес под арендой; вход и выход узла публикуются сигналом `system/members`; истечение аренды — окончательный признак отказа узла;
- маршрут запроса — узлы с нужной ролью из состава кластера, владелец ключа — по rendezvous-хэшированию, при отказе — следующий; параллельность обработки ограничена, при превышении — ответ «занят», который вызывающий переводит во временный отказ;
- матрица разрешений задаёт, какая роль вызывает какие службы и подписывается на какие темы (минимальные привилегии, п. 6.8).

Закрытый список таймеров:

1. аренды — продление и истечение (кластерные аренды, аренды секретов);
2. отложенные повторы — доставка SMTP по расписанию RFC 5321, повтор при временных ошибках внешних систем; один таймер на ближайший срок, а не периодический проход;
3. таймауты и сроки — сессии, запросы, операции;
4. расписание фоновых работ из конфигурации — проверка целостности, поиск «сирот», обновление сертификатов; удаление по сроку (корзина, GC с отсрочкой) — один таймер на ближайший срок;
5. наблюдение за источником без уведомлений — только при отсутствии событий ОС (файлы конфигурации и сертификатов — inotify, давление ресурсов — триггеры PSI cgroups), интервал — из конфигурации.

**Обоснование.** Сигналы через PostgreSQL не добавляют продукта и точки отказа: сигналы недоступны только вместе с PostgreSQL, без которого не работает и остальная система. Ограничение NOTIFY — сериализация фиксации транзакций с NOTIFY — снимается отправкой из отдельного публикатора вне почтовых транзакций. Расчётная нагрузка (до 50 000 ящиков, около 400 изменений в сутки на ящик) — до 2 000 сигналов в секунду в пике, требование к задержке — менее 1 с. Транспорт пересматривается, если на испытаниях Д.6 доля времени фиксации на primary, занятая NOTIFY, превысит 5 % или задержка сигнала p99 превысит 1 с; контракт сигналов при этом не меняется. Отдельный брокер (Valkey) и собственная сеть узлов отклонены (приложение Б). Сигналы шарда разделяют судьбу его данных: при отказе шарда недоступны и его ящики, а отказ центральной шины лишал бы сигналов все шарды сразу; поэтому шина в ядро не входит. Условия пересмотра — приложение Д (Д.7), включая число соединений-слушателей (узлы × шарды) больше 2 000; кандидат — NATS JetStream как реализация того же контракта сигналов, журнал событий остаётся в PostgreSQL. Внешние потребители событий подключаются модулем «Коннектор событий» (п. 1.3).

## 2.9. Схемы развёртывания

Профиль и схема выбираются по масштабу и требованию отказоустойчивости; бинарный файл один, схемы различаются конфигурацией. Схемы, состав, ограничения и поведение при отказах — приложение З.

**Таблица: Схемы развёртывания**

| Схема | Назначение | Отказоустойчивость |
|---|---|---|
| SMB | До 1 000 ящиков, одна ВМ | Средствами гипервизора (перезапуск ВМ) и резервного копирования |
| Малый Enterprise | Небольшая организация с требованием отказоустойчивости | Отказ любой одной ВМ без потери данных |
| Enterprise-ВМ | От 1 000 ящиков, роли по пресетам | Отказ узла любой роли, переключение СУБД ≤ 30 с |
| Enterprise-K8s | Динамическая нагрузка | То же; самовосстановление и масштабирование средствами Kubernetes |
| DR active-passive | Резервная площадка | Переключение площадок по процедуре; RPO — отставание репликации |
| Метро-кластер | Две площадки с задержкой ≤ 5 мс и свидетель на третьей | Отказ площадки без потери данных, автоматически |
| Гео active-active | Площадки с большой задержкой, работа на обеих (модуль «Геораспределение») | Отказ площадки затрагивает только её ящики |

Узел — экземпляр `thepost` с набором ролей по пресету (п. 2.1). Узел и шард (п. 3.6) имеют атрибут площадки `site`. В схеме гео active-active у ящика есть домашняя площадка — площадка его шарда; запись данных ящика между площадками не выполняется:

- сессия обслуживается на домашней площадке;
- узел чужой площадки перенаправляет клиента JMAP, CalDAV, CardDAV и Admin API на адрес домашней площадки (сессия JMAP, well-known), проксирует сессии IMAP и submission после аутентификации, а письма, принятые по SMTP, пересылает по внутреннему SMTP с mTLS на transport домашней площадки;
- каталог (шард 0) читается с локальной реплики, запись — на primary;
- тела писем пишутся в BLOB-хранилище площадки и реплицируются асинхронно; отсутствующий локально объект читается с соседней площадки;
- лидер maintenance выбирается по площадке.

**Обоснование.** У каждого шарда один пишущий primary, поэтому работа на нескольких площадках достигается разнесением ящиков по площадкам (модель групп доступности баз Exchange), а не шиной или многомастерной репликацией: последняя порождает конфликты UID и MODSEQ. При разрыве связи каждая площадка продолжает обслуживать свои ящики. Атрибут площадки в базовой поставке исключает переработку состава кластера и справочника шардов при подключении модуля.
