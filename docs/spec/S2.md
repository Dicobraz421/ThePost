# 2. Архитектура

## 2.1. Модульный монолит с ролями

Ядро — модульный монолит: единая кодовая база и единый бинарный файл, функции которого разделены на роли. Набор ролей узла задаётся в config.yaml. В профиле SMB все роли работают в одном процессе; в Enterprise каждая роль развёртывается и масштабируется отдельно.

**Таблица: Роли ядра**

| Роль | Назначение | Состояние |
|---|---|---|
| smtp-in | Приём почты (25); проверка SPF, DKIM, DMARC, ARC; вызов Milter; выполнение Sieve; доставка. Режим edge — п. 2.6 | Без состояния; в режиме edge — локальная очередь |
| submission | Отправка клиентами (587, 465) с аутентификацией SASL; ограничение частоты отправки | Без состояния |
| smtp-out | Обработка очереди исходящей почты, DKIM-подпись, MTA-STS, DANE, повторы, DSN | Без состояния, очередь в PostgreSQL |
| imap | IMAP4rev2; POP3 (выключен по умолчанию) | Без состояния, долгоживущие соединения |
| jmap | JMAP Core, Mail, Submission, Push, Sieve, Calendars, Contacts, Tasks | Без состояния, долгоживущие соединения push |
| dav | CalDAV, CardDAV, scheduling, free/busy, GAL | Без состояния |
| admin | Admin REST API, экспорт и импорт; операции модулей | Без состояния |
| search | Выполнение поисковых запросов по индексам ящиков | Кэш индексов на NVMe (производные данные) |
| indexer | Построение индексов; извлечение текста вложений в изолированных подпроцессах (п. 2.7) | Без состояния, задания в PostgreSQL |
| maintenance | GC, поиск «сирот», verify; фоновые задания модулей (миграция бэкенда, перенос ящиков) | Без состояния, лидер — по лизе в PostgreSQL |

Источник истины — PostgreSQL и BLOB-хранилище; любой узел обслуживает любой ящик. Уведомления об изменениях (JMAP push, IMAP IDLE) между узлами передаются через шину событий: Valkey в Enterprise, внутри процесса — в SMB.

Слой данных — PostgreSQL, BLOB-хранилище, Valkey, хранилище секретов — внешний и не является ролью продукта. В профиле SMB эталонная установка размещает PostgreSQL и OpenBao на той же ВМ (п. 1.2).

Набор ролей узла задаётся параметром `roles` в config.yaml: пресетами, отдельными ролями или их сочетанием.

**Таблица: Пресеты ролей**

| Пресет | Роли | Размещение |
|---|---|---|
| all | Все роли | SMB: одна ВМ |
| edge | smtp-in в режиме edge (п. 2.6) | DMZ |
| transport | smtp-in, smtp-out | Внутренний контур; фиксированные egress-IP |
| access | submission, imap, jmap, dav, admin | Внутренний контур, за L4-балансировщиком |
| backend | search, indexer, maintenance | Внутренний контур |
| mailbox | transport + access + backend | Минимальный Enterprise: узлы edge и mailbox |

Пресеты mailbox и edge соответствуют ролям Mailbox и Edge Transport Microsoft Exchange; пресеты transport, access и backend применяются для раздельного масштабирования.

**Обоснование.** Модульный монолит сохраняет преимущества микросервисов — изоляцию сбоев на уровне процессов, независимое масштабирование ролей, раздельные лимиты ресурсов — без их издержек: нет сетевых вызовов между сервисами, одна версия и один цикл выпуска, один артефакт для всех профилей. Требование единого бинарного файла выполняется без противоречий.

## 2.2. Среда выполнения

Целевые платформы — Linux x86_64 и AArch64. Сборка под другие ОС не выполняется и не тестируется. Доступ к ОС (сеть, диск, сигналы, распределение памяти) изолирован в отдельном модуле (crate); логика протоколов не содержит системных вызовов и тестируется без ОС.

Асинхронный рантайм — Tokio (epoll). Использование io_uring не является требованием и допускается после стабилизации его поддержки в рантайме; изменения затрагивают только системный модуль.

**Обоснование.** Одна платформа сокращает матрицу сборки и тестирования и позволяет использовать механизмы Linux (seccomp для sandbox, cgroups). Изоляция системного кода обеспечивает тестируемость логики протоколов и локализует изменения при смене рантайма. Переносимость для потребителя обеспечивается OCI-образом.

## 2.3. Варианты развёртывания Enterprise

Поддерживаются два равноправных варианта:

- Enterprise-ВМ — бинарный файл на N виртуальных машинах под systemd за L4-балансировщиком; масштабирование добавлением ВМ;
- Enterprise-K8s — роли как отдельные Deployment в Kubernetes (Helm-чарт), HPA по CPU и числу соединений, anti-affinity по узлам, rolling-обновление.

**Обоснование.** Kubernetes оправдан при динамической нагрузке: автоматическое масштабирование, самовосстановление, обновление без простоя. Обязательный Kubernetes стал бы главным источником сложности для заказчиков без собственной платформы; вариант на ВМ по модели эксплуатации соответствует серверам Exchange, но без состояния на узлах.

## 2.5. Точки расширения

Дополнительные модули (п. 1.3) подключаются только через точки расширения ядра:

- интерфейсы (крейт tp-contracts): BlobStore, Directory, SearchIndex, EventSink; модуль добавляет реализацию, не изменяя ядро;
- реестр ролей, capability JMAP и маршрутов Admin API: модуль регистрирует собственные роли, capability и маршруты;
- события ядра — доставка, отправка, изменение флагов, перемещение, удаление в корзину, окончательное удаление, создание и удаление ящика; событие записывается в таблицу outbox в той же транзакции, что и изменение; подписчики (индексатор, модули) читают события с сохранением позиции; доставка не менее одного раза, порядок — в пределах ящика;
- точки принятия решений — синхронные проверки, в которых модуль может запретить или дополнить операцию: перед окончательным удалением (Legal Hold, политики хранения), при доставке и отправке (журналирование); при отсутствии модулей проверка не выполняет действий;
- данные модуля — в отдельной схеме PostgreSQL (`mod_<имя>`) с собственной последовательностью миграций; требования совместимости — п. 6.6;
- конфигурация модуля — секция `modules.<имя>` в config.yaml, описанная в JSON Schema (п. 5.5).

**Обоснование.** События в outbox в одной транзакции с изменением гарантируют, что модуль не пропустит изменение и не увидит неподтверждённое. Отдельная схема БД изолирует данные модуля и позволяет отключить или удалить модуль без изменения схемы ядра.

## 2.6. Пограничный узел (edge)

Узел с пресетом edge размещается в DMZ и принимает почту из интернета:

- узел не имеет доступа к PostgreSQL, BLOB-хранилищу и Valkey; их адреса в конфигурации узла отсутствуют;
- выполняются приём на порту 25, TLS, проверки SPF, DKIM, DMARC, ARC, вызов Milter, ограничение частоты, проверка получателя;
- принятое письмо фиксируется в локальной очереди на диске (fsync до ответа 250) и передаётся по SMTP с взаимной аутентификацией TLS на узлы transport с повторами; выполнение Sieve и доставка — на узлах transport;
- проверка получателей выполняется по реплике списка адресов: узлы transport передают на edge подписанный снимок адресов и доменов (без иных атрибутов учётных записей) и инкрементальные обновления; соединения инициируются из внутреннего контура; при недоступности внутреннего контура edge работает по последнему снимку;
- исходящая почта отправляется узлами smtp-out напрямую с egress-IP либо через edge в режиме ретрансляции (настройка);
- приём распределяется между несколькими узлами edge записями MX; письма в очереди отказавшего узла доставляются после его восстановления.

**Обоснование.** Требования сегментации сети не допускают доступа узла DMZ к хранилищам данных. Модель соответствует роли Edge Transport Microsoft Exchange (синхронизация получателей — аналог EdgeSync).

## 2.7. Ресурсы и изоляция ролей

- невключённая роль не создаёт пулов соединений, кэшей, потоков и слушающих портов; страницы кода невключённых ролей не загружаются в резидентную память;
- лимиты кэшей и пулов задаются по ролям; значения по умолчанию рассчитываются от ресурсов узла с учётом набора ролей;
- резидентная память (RSS) узла с одной ролью без нагрузки — не более 64 MB (уточняется на стенде, приложение Д);
- извлечение текста вложений выполняется в пуле отдельных подпроцессов (подкоманда того же бинарного файла): seccomp, лимиты памяти и CPU (rlimit, cgroups), таймаут, без доступа к сети и записи на диск; аварийное завершение подпроцесса не влияет на основной процесс, документ отмечается как неизвлечённый, подпроцесс перезапускается;
- разбор MIME выполняется в основном процессе (библиотека mail-parser, безопасный по памяти код).

**Обоснование.** Размер бинарного файла не определяет потребление памяти: код загружается по требованию, а RSS формируют кэши, пулы и буферы соединений. Тот же подход применяется в Grafana Mimir и Loki. Отдельный подпроцесс для разбора недоверенных форматов (PDF, Office) исключает влияние уязвимостей и сбоев парсеров на работу узла, в том числе в профиле SMB, где все роли работают в одном процессе.
