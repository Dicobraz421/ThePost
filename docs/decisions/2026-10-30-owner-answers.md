# 2026-10-30 — ответы владельца на вопросы волн 01–03

Основание — вопросы агентов (issues с меткой `решение`, #21–#40). Номер — issue.

## Контракты и данные
- #21 В `tp-contracts` подключаются `tokio` (sync), `tokio-util` и `serde_json`: `RoleCtx` на `watch::Receiver`/`CancellationToken`, `ModuleCtx::config::<T: DeserializeOwned>()`, `serde_json::Value` в JMAP-capability. Критерий выбора — стабильнее и быстрее.
- #22 `ModSeq` — один счётчик на учётную запись (и для папок IMAP, и как состояние JMAP).
- #23 Событие журнала пишет `tp-meta` в той же транзакции, что и изменение; `append(tx)` в контракт не выносится.
- #24 `gen` → `generation`, `Commit::Done { generation }`, `mark_deleting(key, older_than)`.
- #25 `Authorizer::send_right(principal, from)` для Send As / Send on Behalf; `SaslServer` в контрактах.
- #30–#33 Надгробия BLOB в `finalize_delete`, сохранение `MessageId` при переносе в корзину, проверка RLS-роли в `doctor`, каскадное удаление папок по флагу (подтверждение — у клиента) — как в #17.
- #35 Сегменты индексов (`*_raw`) неизменяемы; кэш BLOB их кэширует. Неизменяемость закрепляется в `docs/CONTRACTS.md`.

## Платформа и наблюдаемость
- #26 В `tp-sys` подключаются `serde` (разбор секций) и `tracing`.
- #27 Логи — stdout (JSON) → journald → syslog. OTLP-экспорт логов не делается; OTLP — только трейсы, опционально.
- #28 Секции `telemetry`, `service_http` (`0.0.0.0:8081`), `reload` (`poll_interval_ms: 5000`); переменные `THEPOST_<A>__<B>`, `THEPOST_CONFIG` — путь к файлу.
- #29 Режим проверки конфигурации `thepost config check`: строгий, ошибка на неизвестные и неверные поля. При запуске сервер неизвестные поля пропускает с предупреждением в лог.
- #39 Метрики шины Valkey регистрируются в общем реестре платформы, без новых зависимостей в `tp-cluster`.

## Кластер, CI, развёртывание
- #34 Профиль dev в compose создаёт бакет S3 для интеграционных тестов (карточка полосы deploy).
- #38 В CI job `test` поднимается сервис Valkey; интеграционные тесты шины идут в CI.
- #40 Сообщение шины — компактный текст с версией формата (`1|<tenant>|<account или ->|<вид>`).

## Шифрование любого обмена
Требование владельца: любой обмен должен быть скрыт.
- Все внутренние каналы — только TLS по умолчанию: узел ↔ PostgreSQL (`sslmode=verify-full`), узел ↔ Valkey (`rediss://`), узел ↔ S3 (только `https://`), узел ↔ узел (SMTP edge → mailbox — mTLS, SRS 2.6), служебный HTTP (`/metrics`, `/healthz`).
- Открытый канал — только профиль dev: явная настройка в секции канала и предупреждение в лог при каждом запуске. В остальных случаях адрес без TLS — ошибка конфигурации (`thepost config check` и старт).
- Сертификаты — те же механизмы, что для клиентского TLS (SRS 6.2): ACME, файлы, секреты Kubernetes с перечитыванием.
