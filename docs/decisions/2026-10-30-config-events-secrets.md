# 2026-10-30 — длительности в конфигурации, doctor, разделы журнала, секреты

Основание — вопросы волны meta-02 (PR #42, issues #43–#45) и требование владельца по секретам.

## Длительности в конфигурации (#43, вариант 2)
- Длительности в config.yaml — строки humantime: `5s`, `250ms`, `10m`, `24h`; единый формат для всех крейтов.
- Сериализация и JSON Schema (`type: string`, шаблон) — общий модуль `tp_contracts::config::duration` без новых зависимостей (CTR-13).
- Поля называются без единицы: `acquire_timeout: 5s`. Ранее принятое `reload.poll_interval_ms: 5000` (#28) приводится
  к тому же виду: `reload.poll_interval: 5s`.

## Права роли приложения в doctor (#44, вариант 1)
- Роль приложения с SUPERUSER или BYPASSRLS — `Fail` всегда: RLS не изолирует организации.
- Стенды разработки и эталонная поставка подключаются отдельной ролью без этих прав (DEP-07).

## Разделы журнала событий между экземплярами (#45, вариант 3)
- Разделы подписчика назначает tp-cluster: rendezvous-хэширование ключа `<подписчик>/<раздел>` по живым узлам (CLU-02).
- Живые узлы — членство с периодическим продлением записи узла в PostgreSQL (контракт CTR-14, реализация META-16).
- Лиза раздела остаётся: назначение решает, кто берёт раздел, лиза с номером захвата гарантирует, что раздел
  обрабатывает один экземпляр и при смене владельца (переходный период) — без двойной фиксации позиции.
- Экземпляр отдаёт лизы разделов, которые ему больше не назначены; с одним узлом (SMB) ему назначены все разделы.

## Секреты — только через хранилище секретов
Требование владельца: пароли шардов и прочие секреты — только через vault.
- Хранилище — готовое: **OpenBao** (MPL-2.0, проект Linux Foundation, API совместим с HashiCorp Vault — подходит и
  существующий Vault заказчика). Своё хранилище не пишем: шифрование, распечатывание, политики доступа и аудит — это
  отдельный продукт с высоким риском ошибок безопасности.
- OpenBao — часть эталонной поставки: сервис в compose, чарт в Helm, роль в Ansible (DEP-07); слой данных, как
  PostgreSQL и Valkey, внешний для бинарного файла `thepost`.
- Секреты, которые идут только через хранилище: пароли и адреса с паролями PostgreSQL (основная БД и шарды), ключи S3,
  пароль Valkey, закрытые ключи DKIM и учётной записи ACME, ключи подписи токенов, секреты LDAP/OIDC и внешних систем.
  Сертификаты TLS — по SRS 6.2 (ACME, файлы, секреты Kubernetes); закрытые ключи к ним — тоже из хранилища, если
  администратор не выбрал секреты Kubernetes.
- В config.yaml и в таблицах БД — только ссылки на секреты: `{ secret: "<путь>#<поле>" }` (контракт `SecretStore`,
  CTR-15). Значение секрета в открытом виде в конфигурации — ошибка `thepost config check` и старта.
- Справочник шардов хранит адрес шарда без пароля и ссылку на секрет с учётными данными (META-17).
- Вход узла в хранилище: Kubernetes auth (Helm), сертификат TLS узла (mTLS; сертификаты уже обязательны по решению
  «Шифрование любого обмена»), AppRole с `secret_id` из файла (systemd credentials) для установки без Kubernetes.
- Канал к хранилищу — только TLS; профиль dev — OpenBao в dev-режиме в compose, тесты полос — `MemSecretStore` из tp-testkit.
- Секреты читаются при старте и при перечитывании конфигурации; аренды (lease) секретов продлеваются; `thepost doctor`
  проверяет доступ к хранилищу и что в конфигурации нет секретов в открытом виде.
- Учётные данные PostgreSQL — статический пароль в KV по умолчанию; динамические учётные данные (database secrets
  engine, короткоживущие пароли с ротацией) — по настройке (META-18).
