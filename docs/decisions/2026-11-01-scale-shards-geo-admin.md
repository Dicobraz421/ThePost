# 2026-11-01. Масштабирование, шарды, геораспределение, администрирование

Решение владельца (обсуждение 2026-11-01).

## Масштабирование (SRS 2.3, 2.9, приложение З)
- Kubernetes: HPA по CPU; по числу соединений — по выбору заказчика (prometheus-adapter); окно стабилизации при сжатии.
  HPA по памяти не используется: память занята кэшами до лимита и не освобождается после пика; память — requests и limits,
  размеры — рекомендации VPA.
- Схемы развёртывания: SMB, малый Enterprise, Enterprise-ВМ, Enterprise-K8s, DR active-passive, метро-кластер,
  гео active-active (модуль). Профиль выбирается по масштабу и требованию отказоустойчивости, бинарный файл один.
- Малый Enterprise: 2 узла `mailbox`, PostgreSQL primary + standby + монитор, SeaweedFS на трёх ВМ данных
  (метаданные filer — в PostgreSQL), узлы edge — по необходимости.

## Чтение с реплик (SRS 3.1)
- `ReadIntent::{Primary, Stale}`. Протокольные чтения (IMAP, JMAP, DAV, SMTP) — только primary.
- `Stale` — закрытый список фоновых чтений: экспорт, отчёты Admin API, eDiscovery, verify, поиск «сирот», первичная индексация;
  выполняются на реплике при отставании ≤ 30 с (настройка), иначе и при конфликте с восстановлением — на primary.
- Отклонено: чтение протокольных запросов с реплик. Пересмотр — если primary упирается в чтение, а не в запись (Д.6).

## Шарды и организации (SRS 3.6, 3.8)
- Шард — кластер PostgreSQL (primary и реплики под HA заказчика). Шард 0 — основная БД с каталогом.
- Справочник шардов в основной БД → сигнал → ленивые пулы. Базовый код всегда работает через справочник;
  один шард и одна организация — вырожденный случай. Модуль «Шардирование» добавляет размещение, перенос, Admin API.
- Размещение: всё, что меняется в одной транзакции с ящиком, — на шарде ящика (папки, письма, журнал изменений, ACL, корзина,
  манифест индекса, журнал событий ядра, очередь исходящей почты отправителя, учёт ссылок на BLOB). В основной БД — каталог,
  справочник шардов, состав кластера, аренды, блокировки, настройки транспорта, пароли приложений.
- Учёт ссылок BLOB — на каждом шарде; объект живёт, пока на него ссылается хотя бы один шард.
- Организация и шард — независимые оси: по умолчанию организации делят шарды (RLS); организацию можно закрепить за группой шардов
  (требования физического разделения) с отдельным бакетом или префиксом BLOB.

## Сигналы и шина (SRS 2.8)
- Шина в ядро не входит: сигнал шарда разделяет судьбу его данных. Критерий пересмотра дополнен числом соединений-слушателей
  (узлы × шарды > 2000). Кандидат при срабатывании — NATS JetStream как реализация `EventBus`; outbox в PostgreSQL остаётся.
- Внешние потребители событий — модуль «Коннектор событий» (журнал событий → Kafka, NATS, вебхуки).

## Геораспределение (SRS 2.9, приложение З)
- Поддерживаемые схемы: DR active-passive, метро-кластер (задержка ≤ 5 мс, свидетель на третьей площадке).
- Атрибут `site` у узла и шарда — в базовой поставке.
- Модуль «Межсайтовый DR» расширяется до «Геораспределения»: домашняя площадка ящика; сессия обслуживается на домашней
  площадке, чужая площадка перенаправляет (JMAP, DAV, Admin API), проксирует (IMAP, submission) или пересылает (SMTP);
  чтение BLOB с соседней площадки; каталог — с локальной реплики; лидер maintenance — по площадке.
- Отклонено: мультимастер PostgreSQL, шина как средство геокластера.

## Администрирование (SRS 5.2)
- CLI `thepost admin` — подкоманда бинарного файла, клиент генерируется из OpenAPI (progenitor), Ф1.
- Веб-консоль администратора — базовая поставка, Ф2: Refine, статика вшита в бинарный файл, раздаётся ролью admin, без CDN;
  выделена из модуля «Веб-клиент».
